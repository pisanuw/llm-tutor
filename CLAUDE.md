# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

A generic, supervised AI tutor that anyone can configure for their own course. It
ships with a small made-up example (two introductory astronomy courses, `AST101`
and `AST102`, taught by a fictional "Dr. Alex Morgan"; the tutor is "Astra").
Adopters replace the example content; they should not need to change Python.
[ADDING-KNOWLEDGE.md](ADDING-KNOWLEDGE.md) is the adopter's guide and must stay
accurate when you change how content is read: update it in the same change.

**Never hardcode a course id, a lecture count, the subject, the instructor's name,
or an institution** in code, templates, prompts or tests outside the fixture. Read
them from `tutor.courses` (`IDENTITY`, `COURSES`, `COURSE_LIST`, `DEFAULT_COURSE`,
`course_label`, `course_context`, `lecture_numbers`) in Python, and from the Jinja
globals `tutor`, `course_list`, `course_label`, `course_color` in templates.

## Commit message convention

All commits must follow **Conventional Commits**. CI checks every pushed commit's subject (`scripts/repo_guard.py`, which also fails on a file over 10 MB, a jump of more than 200 tracked files without an `Allow-Bulk-Add: <reason>` trailer, and paths that look like student records); `.githooks/commit-msg` catches a bad subject before you commit.

```
type(scope): short description
```

Types: `feat` `fix` `chore` `docs` `refactor` `test` `perf` `ci` `style` `revert`

Scopes (optional, lowercase): `agent` `pipeline` `auth` `db` `ui` `mastery` `book` `deploy` `content`

To install the hook after a fresh clone:
```bash
git config core.hooksPath .githooks
```

## Two parallel deliverables in one repo

1. **`pipeline/`**: offline content CLI (`python -m pipeline --help`). Ingests an instructor's source files, builds the ChromaDB knowledge base, drafts lecture plans, learning goals, exercises, mastery-check questions, Teach-me openers, slide decks and narration scripts, renders decks, and validates content (`check-content`).
2. **`tutor/`**: FastAPI web app that serves the course interactively to students through a supervised Claude agent, plus instructor and admin pages.

They share the content (below), `knowledge-base/chromadb/` and `output/`, but otherwise run independently.

## The content model

Everything an instructor writes lives under one **content root** ([tutor/paths.py](tutor/paths.py)): the repository root by default, or `TUTOR_CONTENT_DIR`.

| Path (under the content root) | Read by |
|---|---|
| `courses.yaml` | `tutor/courses.py` (app) and `pipeline/config.py` (pipeline). Tutor identity (name, instructor, subject, audience, timezone, code_language, site_url, avatar) and the course list (id, label, title, lectures, topics, note, sources). Validated at import; a bad file stops the app at boot. |
| `persona/{persona-distilled,communication,teaching}.md` | the system prompt (`tutor/agent/prompt_builder.py`) |
| `instructor-profile/{transcripts-voice,lecture-flow,teaching-patterns,examples-library,topic-explanations}.md` | the system prompt |
| `curriculum/<COURSE>-lecture-plan.md` | `get_lecture_outline`, lecture titles (`tutor/agent/lecture_plan.py`), `extract-goals`, slide/script generation |
| `curriculum/learning_goals.json` | seeded into `learning_goals`/`goal_prerequisites` on a first boot (`startup.seed_learning_goals_if_empty`; later edits via `python -m pipeline.seed_goals`) |
| `curriculum/tracks.json` | upserted at every boot (`startup.seed_tracks_if_empty`); `<COURSE>-lecture-order` is every student's default track |
| `curriculum/exercises.json`, `exercise_tests.json` | `get_exercise`, `run_code` |
| `curriculum/starter_prompts.json`, `source-lecture-map.json`, `pedagogy_moves.yaml`, `teachme/`, `mastery_exams.json` (generated, gitignored) | starters, slide-panel mapping, strategist playbook, Teach-me openers, mastery checks |
| `explorables/<goal_id>.html` | `/explorables` mount, the map |

Goal ids are `<COURSE>-L<NN>-<slug>`; course ids are 1 to 8 letters or digits (varchar(8) columns, URL segments, file prefixes). `python -m pipeline check-content` ([pipeline/check_content.py](pipeline/check_content.py)) validates all of it; extend it when you add a content file or field.

**Tests never read the adopter's content.** `tests/conftest.py` sets `TUTOR_CONTENT_DIR=tests/fixtures/content`, a frozen copy of the example course with `code_language: C++` and a few extra exercises the tests need. Module-level paths are computed at import, so the variable must be set before `tutor` is imported (conftest does). Change the fixture only when a test needs it; never make a test depend on the root content.

## Common commands

```bash
# Content pipeline
python -m pipeline check-content                  # validate courses.yaml, curriculum/, persona/, ... (free, no model calls)
python -m pipeline ingest --course AST101         # source-materials -> knowledge-base/raw (needs requirements.txt)
python -m pipeline index --rebuild                # knowledge-base/raw -> knowledge-base/chromadb; writes manifest.json
python -m pipeline extract-goals                  # lecture plans -> learning_goals.json (claude CLI)
python -m pipeline init-tracks                    # a <COURSE>-lecture-order track per course
python -m pipeline build-exercises                # templated exercises per goal (no model call)
python -m pipeline generate-mastery-exams --resume
python -m pipeline render-html --course AST101    # content.md -> index.html (local)
python -m pipeline status --verbose

# Web app (the /api/chat curl needs an admin session cookie; students get 403)
.venv/bin/uvicorn tutor.main:app --reload         # http://localhost:8000/auth/login
./run-locally.sh                                  # the same, forced onto a throwaway SQLite DB
curl -s -b "session_token=..." -X POST http://localhost:8000/api/chat \
     -H 'Content-Type: application/json' \
     -d '{"message": "why does the Moon have phases?", "course": "AST101"}'

# Activity analytics (docs/analytics-cookbook.md): a local, pseudonymous SQLite copy, then offline reports
python -m tutor.analytics export --out ~/tutor-data/tutor.sqlite            # reads DATABASE_URL, read-only; incremental
python -m tutor.analytics class 3 --db ~/tutor-data/tutor.sqlite --days 14   # also: compare, student, lectures, questions, disengagement, timeline, visits
python -m tutor.analytics daily --db ... --format html --out ~/tutor-data/daily.html --open

# Data handling (docs/retention-policy.md; all read DATABASE_URL; writes are dry runs unless --confirm)
python -m scripts.download_conversations                       # Markdown out of the repo, pseudonymous by default
python -m scripts.set_mastery --student ada@example.edu --lecture 2 --list
python -m scripts.delete_student_data demo@example.edu --messages-only --confirm
python -m scripts.login_report --days 3

# Tests
pip install -r requirements-dev.txt               # the web app's deps, the pipeline modules the tests import, pytest, ruff, mypy
pytest                                            # full network-free suite on tests/fixtures/content
pytest tests/test_pptx_writer.py::test_name       # single test
ruff check . && mypy                              # lint and type check (CI gates both)
```

## Local setup notes

- **Python 3.11.** CI and the production image are 3.11 ([Dockerfile](Dockerfile)), and `[tool.mypy]` pins `python_version = "3.11"`.
- **`tests/test_boot_resilience.py` runs the real `entrypoint.sh` under `dash`.** It needs GNU tar first on `PATH` (macOS ships bsdtar, which rejects `--warning=no-unknown-keyword`; `brew install gnu-tar` and put its `gnubin` at the front of `PATH`) and `python3` on `PATH` to be the venv's (the entrypoint calls bare `python3 -m tutor.migrate`). Activate the venv, or run `PATH=.venv/bin:$PATH pytest`.
- **Browser tests** (`tests/browser_support.py`) skip without Playwright and Chromium (`pip install playwright && playwright install chromium`); they are how to check the 390px rule below.
- **The code sandbox is Linux-first.** Namespaces and `RLIMIT_NPROC`/`RLIMIT_AS` caps apply on Linux only; on macOS the fork-bomb and memory tests are skipped (`@linux_only`) and a local pass is not containment. See [docs/sandbox.md](docs/sandbox.md).
- **`tests/test_retrieval_golden.py`** is opt-in (`RUN_RETRIEVAL_EVAL=1`, and a built store at `knowledge-base/chromadb`): it measures the adopter's knowledge base against `evals/golden_retrieval.json`, not the code. `python scripts/retrieval_eval.py` runs the same evaluator directly.
- **The suite never reads generated artifacts at the repository root.** conftest points `TUTOR_OUTPUT_DIR` (decks) and `TUTOR_CHROMA_DIR` (the vector store) at empty temp folders; a test that needs a deck or a store builds one in `tmp_path` and points the config at it.

## Required environment

`.env` must contain at minimum: `ANTHROPIC_API_KEY`, `SECRET_KEY`, `ADMIN_TOKEN`. [tutor/config.py](tutor/config.py) raises on startup without the first two and warns without `ADMIN_TOKEN` (token access to /admin is then off). Set `ADMIN_EMAILS` too: it has no default in code, and with it empty nobody can open /admin (boot logs a warning). Optional: `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` (else magic-link auth only), `RESEND_API_KEY` + `FROM_EMAIL` (else dev mode prints the magic-link URL on the page), `GITHUB_TOKEN`, `DISCORD_TOKEN`, `TUTOR_CONTENT_DIR`. Voice/TTS: `ELEVENLABS_API_KEY`/`ELEVENLABS_VOICE_ID` (both required to enable the per-reply speaker button), `TTS_CACHE_DIR` (default `tts-cache/`). Code execution: `ENABLE_CODE_EXEC` (default off). Logging: `LOG_LEVEL` (default `INFO`) and `LOG_CONVERSATION_CONTENT` (default `false`; when `true`, the `tutor.activity` event stream also carries message and reply text; events carry `student_id`, never an email), see [tutor/logging_config.py](tutor/logging_config.py). Postgres pool: `DB_POOL_SIZE` (3), `DB_MAX_OVERFLOW` (4), `DB_POOL_TIMEOUT` (10 s), `DB_POOL_RECYCLE` (300 s); keep the pool well under your pooler's cap (DEPLOY.md). Activity events: `ACTIVITY_EVENTS` (default `on`), `ACTIVITY_HEARTBEAT_S` (default 60, floor 10), `ACTIVITY_EVENTS_DAYS` (unset: raw rows age out with the one-year anonymization).

Who the tutor is, the courses, and the class's time zone are **not** environment settings: they are in `courses.yaml`.

## Architecture notes that span files

- **Configuration split.** Three sources, each with one job. [courses.yaml](courses.yaml) (at the content root, see below) names the tutor and the courses; the app reads it through [tutor/courses.py](tutor/courses.py) (`IDENTITY`, `COURSES`, `COURSE_LIST`, `DEFAULT_COURSE`, `course_label`, `course_context`) and the pipeline through `get_course_config` in [pipeline/config.py](pipeline/config.py). [config.yaml](config.yaml) holds the pipeline's own knobs (knowledge-base folders, Whisper, slide counts), surfaced via accessors that resolve paths against the project root; the app does **not** read it. [tutor/config.py](tutor/config.py) loads deployment settings from `.env`. Never hardcode a course id, a lecture count, the subject, or the instructor: read them from `tutor.courses`.

- **ChromaDB is the integration point.** Both the generation pipeline and the tutor agent read from `knowledge-base/chromadb/`. The seven collections (`slides`, `transcripts`, `textbook`, `assignments`, `documents`, `code`, `forum`) are listed once, in [tutor/kb.py](tutor/kb.py): the pipeline's indexer builds exactly those (one builder each in `pipeline/knowledge_base/indexer.py`, each reading `knowledge-base/raw/<collection>/`, and a test holds the two equal), and `find_topic` searches all of them. `forum` is community content (results carry `community_post`); `slides` hits can move the slide panel. A new collection goes in `tutor/kb.py` with a builder in the indexer. `config.yaml` is for the pipeline only, and every key in it has a reader (a test checks); the embedder and chunk sizes are code, since the build and the app's queries must match.

- **Two transcript JSON formats coexist.** Pipeline-generated transcripts include a `source_file` key; bare `whisper` CLI output does not. [pipeline/knowledge_base/indexer.py](pipeline/knowledge_base/indexer.py) handles both. `index` and `index-transcripts` read the pipeline's own folder under `knowledge-base/raw/transcripts/`, then every `knowledge-base/transcripts/<course>-<term>/` folder whose prefix is a course id; a folder without one is listed as not indexed.

- **One embedder builds and queries the store.** The indexer embeds with Chroma's ONNX all-MiniLM-L6-v2, the function `find_topic` queries with (sentence-transformers is gone). A file that is not the JSON its collection expects is skipped and listed, and `index` exits 1. `index --rebuild` drops the collections first, so chunks of a removed file go too. Every build writes `knowledge-base/chromadb/manifest.json` (inputs with hashes, counts, embedder, commit), which the chroma seed carries.

- **`output/<course>/lecture-NN/` is the lecture unit.** Each contains `content.md` (slide source), `index.html` (the Reveal deck the app serves), `script.md` (narration source), optional `audio/`, `frames/slide-NN.png`, `timing.json`, and, only with `--pptx`, the retired `slides.pptx`. A lecture is complete when `content.md` parses to at least one slide and `index.html` exists; `status` and `generate-all --resume` both read that one test in [pipeline/lectures.py](pipeline/lectures.py). Slides are numbered by position when parsed (`html_renderer.parse_slides`), so the deck, the narration clips, and the script's ADVANCE markers agree. Lecture content is gitignored — regenerate via the pipeline.

- **Agent tool loop.** [tutor/agent/turn.py](tutor/agent/turn.py) (`run_turn`) is the single supervised pipeline every endpoint uses: caps, exam intercept, classifier, envelope, gate, actor, detector, judge, telemetry. It only sequences the stages in [tutor/agent/turn_stages/](tutor/agent/turn_stages/) (one module per stage; the package docstring lists them in order), and nothing else may import a stage. The actor model is called only in `turn_stages/actor_client.py`: `stream_round` for the streaming tool loop and `generate_once` for the revise call, the two seams tests fake. Stages reach their collaborators through the module (`state_mod.record_topic_access`), so a test patches `tutor.agent.<module>.<name>`. Tool calls run synchronously (ChromaDB is sub-200ms once warm: `find_topic` embeds the query once with the process's one embedder, `tools._embedder`, and passes `query_embeddings`; never `query_texts` on a collection opened without an embedder, which reloads the ONNX model on every query, and `tools.warm_up()` loads it at boot); the final Claude answer streams. Each turn stores its stage timings in `verdicts.timings` (`TurnRequest.mark`/`add_ms`). The four tools (`find_topic`, `get_lecture_outline`, `get_exercise`, `evaluate_code`) are defined and dispatched in [tutor/agent/tools.py](tutor/agent/tools.py). The system prompt is assembled once at startup by [tutor/agent/prompt_builder.py](tutor/agent/prompt_builder.py) from `courses.yaml`, `persona/` and `instructor-profile/`, then the fixed hint-ladder rules. Its cached prefix has a 1-hour TTL (`CACHE_TTL` in `actor_client.py`), and opening `/chat` warms it with a `max_tokens=0` call (`turn_stages/cache_warm.py`, reached through `turn.warm_prompt_cache`; throttled to one per 50 minutes, ledgered as `cache_warm`, off with `CACHE_PREWARM=false`, which the test suite sets). Every other model call (classifier, judge, strategist, summarizer, exam grader, rubric evaluator, vision, mining, health ping) builds its client with `supervisor_client()` in [tutor/agent/clients.py](tutor/agent/clients.py): 30 s read timeout, one retry. `tests/test_single_actor.py` fails on an `anthropic.Anthropic(` anywhere else. Student-derived text in any prompt (messages, answers, code, transcripts, drafts, the rolling summary) goes through `frame()` in [tutor/agent/framing.py](tutor/agent/framing.py), which stops it closing its own tag; the rolling summary rides in the user turn, never the system prompt.

- **The telemetry ledger holds turns and calls.** `turn_events` has one row per supervised turn (`kind="chat"`: intent, the ceiling enforced, the move, the verdict, the detector, grounding) and one row per supervisor model call made around it (`classify`, `strategist`, `judge`, `cache_warm`, `evaluate`, `exam_classify`), written only so each call's tokens and cost land in the ledger separately. A call has no intent, ceiling or verdict and never had one, so roughly three rows in four carry none: the admin Supervision tab therefore filters by kind and opens on the turns, and a cell that cannot apply reads "n/a" ([tutor/supervision_view.py](tutor/supervision_view.py), the one place the table's wording is decided). `rung_used` is the ceiling that was **enforced**, not the rung a reply reached — nothing measures that, since the actor is told a ceiling and never asked what it used; `envelope.rung_base` keeps the mastery band's ceiling before the floors and caps moved it, so the cell can read "H2→H4". The ceiling itself is the most permissive band among the goals in scope (`policy.compute_envelope`), so one goal with no graded evidence pins a turn at H5 (a new student's turns all run there), and `scripts/set_mastery.py` sets a whole lecture's goals at once (`--all-lectures` for the course, since the goals in scope come from the classifier's reading of the question, not from the lecture you had in mind).

- **Every `claude` CLI launch is locked down.** Pipeline code calls `_generate_via_cli` in [pipeline/generate/script_generator.py](pipeline/generate/script_generator.py), or launches the CLI the same way (`extract_goals`, `generate_mastery_exams`), and the app's local `USE_CLAUDE_CLI` backend does too: every tool denied with `--disallowed-tools` and one shared list, the CLI's permission checks on, and `ANTHROPIC_API_KEY` removed from its environment so the subscription is billed, never the key. [tests/test_cli_hardening.py](tests/test_cli_hardening.py) pins the four places the CLI starts; a new one has to be added there.

- **Database access stays off the event loop.** The app shares one engine (`app_engine` in [tutor/db/models.py](tutor/db/models.py); `get_engine` builds a fresh one for scripts). A route handler that touches the database is a plain `def` (FastAPI runs it in the threadpool) or awaits `run_in_threadpool` for its database part; `tests/test_db_off_loop.py` fails on an `async def` handler that takes `db` without it. Inside `run_turn`, every database step goes through `_db_step`: it runs in the executor and commits (or rolls back) on its own, so a turn never holds a pooled connection while it waits on a model, and the turn keeps `expire_on_commit` off so reading an attribute on the loop never reloads. The classifier and the judge report usage through a `usage_sink` instead of writing through the session. The exam grader's own bookkeeping (`mastery.stream_grade_exam`) still runs on the loop and holds one connection through the grading call; exam answers are rare.

- **Boot never stops on an external.** [entrypoint.sh](entrypoint.sh) seeds each blob atomically (download with retries, unpack into a scratch directory, `python -m tutor.seed_check`, swap, `.seed-ok` marker) and writes problems to `BOOT_WARNINGS`, which the lifespan emails once. The lifespan's database setup (`startup.ensure_database_ready`) is fail-soft, and a healthy `/healthz` finishes it; `/healthz` also reports the knowledge base as `kb` ("ok" when any collection has documents). `tests/test_boot_resilience.py` runs the real entrypoint under dash with `file://` seeds.

- **Alembic runs at boot.** `entrypoint.sh` runs `python -m tutor.migrate` before uvicorn: it stamps a database the app built at boot (no `alembic_version` row) at the baseline, then upgrades to head. Every revision after the baseline is guarded, so author new ones the same way (see `migrations/versions/e8a3c5d1f2b4_*`); `startup.ensure_schema` is only a safety net. `tests/test_migrations.py` diffs a migrated database and an adopted boot-built one against the models.

- **Static mounts.** `tutor/main.py` mounts `output/` at `/slides`, served only to a signed-in student (`GatedRevalidateStaticFiles`), and `find_topic` returns a lecture's Reveal deck in the `/slides/<course>/lecture-NN/index.html` shape; the per-slide PNG frames are gone from the app. `/book` and `/explorables` are public, and `/lecture-audio` is gated like `/slides`; the book's chapter narration (`python -m pipeline render-book-audio`, `output/book/<slug>.mp3`) is served under that gated mount at `/lecture-audio/book/`, and `book/narration.js` shows a player on the public page only when a HEAD probe with the session cookie succeeds. The clips live under `lecture_audio_dir` in config (`LECTURE_AUDIO_DIR`: the persistent disk in production, `output/` locally), which the mount and the `/lectures` catalog both read; the slide seed carries no audio.

- **One web layer.** Every router renders through `templates` in [tutor/templating.py](tutor/templating.py) (anchored on the package, not the working directory). Pages that only vary for a signed-in reader use `session_student()` in [tutor/auth/deps.py](tutor/auth/deps.py); an email lookup is `find_student()` in [tutor/auth/access.py](tutor/auth/access.py); the course list is `COURSES` in [tutor/courses.py](tutor/courses.py). HTML is built in templates, never f-strings (the chat's progress panel is `_progress.html`), JSON inside `<script>` goes through `|tojson`, and a value an inline handler needs travels in a `data-` attribute, not a JS string. `mypy` gates every router. Page scripts live in `tutor/web/static/` (`chat.js`, `map.js`), loaded through `asset_url()` (versioned by content) and scanned by the Tailwind build; the template passes them data through small `window.TUTOR_*` lines or a `<script type="application/json">` block. `chat.js` must stay a blocking script placed after the markup: `tutorApp` has to exist before the deferred Alpine starts.

- **Frontend is responsive; verify every template change at 390px.** One codebase serves phones and desktops. The chat page's split view (slides | chat) collapses below `md` into a single panel with a header toggle (`mobilePanel` in `tutorApp` in [tutor/web/static/chat.js](tutor/web/static/chat.js), `.m-panel-on/.m-panel-off` in [tutor/web/templates/chat.html](tutor/web/templates/chat.html)); base.html provides `.app-vh` (dvh-aware full height), `.pad-safe-b` (home-indicator padding), and forces 16px form fields on phones (iOS zoom). When editing templates: no fixed widths without a `md:` variant, `min-w-0`/`break-words` on flex children that hold code or URLs, and check the result in a 390px viewport before committing. Admin stays desktop-first (tables get `overflow-x-auto` at most).

- **One site header.** Every signed-in page renders its header with `site_header` from [tutor/web/templates/_nav.html](tutor/web/templates/_nav.html) (page controls go in its `{% call %}` slot), and its route passes `nav_context(...)` from [tutor/nav.py](tutor/nav.py). Do not hand-write a `<header>`; `tests/test_site_header.py` fails on one.

- **Voice/TTS path.** The 🔊 button on a finished, saved assistant reply (`finishBubble`/`playTTS` in [tutor/web/static/chat.js](tutor/web/static/chat.js); a reply without a `message_id` gets none) POSTs the reply's `message_id` and text to `POST /chat/tts` ([tutor/routers/chat.py](tutor/routers/chat.py)), which speaks the student's own stored reply by id whatever its age, and otherwise 403s unless the text matches one of the student's 20 most recent assistant messages (the cloned voice never speaks arbitrary text), then calls `synthesize` in [tutor/agent/tts.py](tutor/agent/tts.py). That strips markdown/code (so the voice reads prose, not syntax), hashes voice_id + cleaned text, serves a cached MP3 from `tts-cache/` or calls the ElevenLabs API on a miss. It does **not** touch the token-streaming loop: synthesis is on-demand after the reply completes, and the endpoint returns 503 unless both ElevenLabs env vars are set. `cache_path` in tts.py is the one place the cache key is computed; `python -m tutor.prewarm_tts` (a dry run unless `--spend`) renders the Teach-me openers into that cache through `synthesize`, since `/chat/teachme` stores them verbatim, so the 🔊 button on an opener never bills twice.

- **Activity events.** What a signed-in student does in the browser is recorded in the `activity_events` table: `tutor/web/static/track.js` (loaded by base.html for a signed-in reader) records page views, visibility, a heartbeat, the leave, every click on a control (with the same-origin path a link opens), and a script failure's name, file and line (never its message; `client_error`, capped per page view), and page scripts add their own through `window.tutorTrack` (chat.js: questions, replies on the stream's turn id with the reply's message id, slides cited, a deck that was not there, pickers, voice, feedback); `deck-track.js` runs inside every Reveal deck the `/slides` mount serves (the mount adds the versioned tag to each deck's `index.html`, `tutor/deck_tracking.py`) and records slides shown with their on-screen dwell, narration played, and the close. Batches go to `POST /api/events`, are cleaned against the vocabulary in [tutor/activity_events.py](tutor/activity_events.py) (an event or field outside it is dropped; `label` is a control's static text, the only free text, blanked at anonymization), capped per student, and written in one statement through `state.record_activity_events`. The chat route's `turn_id` is the one the turn runs under and stores on `turn_events.turn_id`, so a browser event joins its ledger row; `done` and `section` events carry the saved reply's `message_id`. Rows carry ids only, never an email or a message's text.

- **Reloads, restarts and double submits.** A page opened or reloaded mid-reply asks `/chat/running` and streams the running reply into a bubble under its question (`reattach` in chat.js), and a "busy" answer names the running turn (`turn_id`) so the page shows it coming. A turn the process loses (a deploy) is closed: uvicorn runs with `--timeout-graceful-shutdown 15` (entrypoint.sh), the lifespan then gives running turns a few seconds and cancels them (`_close_running_turns` in tutor/main.py), and a cancelled turn marks its ledger row `interrupted` and writes `state.INTERRUPTED_NOTE`, but only where the conversation still ends on that turn and dated with its question; a sweep (`state.close_interrupted_turns`, at boot from `startup.ensure_database_ready` and once more 16 minutes later) does the same for turns still `in_progress` after 15 minutes. `db_step` waits for its thread when cancelled, so a step never commits after the turn closed. The page gives a cut-off question back only when its resume found the turn gone (a 404). A form marked `data-submit-once` (sign-in, Continue) sends once, and a second press of a used link or code from the browser it signed in goes on to `next`. On an iPhone, a first play the gesture window refused becomes "tap to play".

- **Error pages.** Every 4xx and 5xx the app answers a browser with, 401s and the browser's own requests (`/favicon.ico`, the touch icon, `/.well-known/`) excepted, is one `request_errors` row written by the exception handlers in `tutor/main.py` through [tutor/request_errors.py](tutor/request_errors.py) (the path with no query and no magic-link token, the same-site referrer, the student when the cookie was live, the user agent's class, a six-character reference); a navigation renders `error.html` with the shared header and a "Tell <instructor>" button (`POST /errors/report`, which alerts the operator), a fetch keeps its JSON. A signed-in student following a same-site link to a 404 emails the operator through `alerts.send_alert` (key `404:<family>`); bots and scanners are counted, never alerted. A browser that closes the connection mid-request (Starlette's `ClientDisconnect`, the leave beacon most often) is never a 500: the unhandled handler answers 400 with no alert or row, and Sentry ignores the class. The admin Today panel and the daily digest list the day's errors; the retention sweep prunes the table at 90 days. `tests/test_request_errors.py` pins all of it.

- **What a student can send, and what Postgres refuses.** Production is Postgres and the suite is SQLite, which accepts a too-long VARCHAR write, an integer past int4 and a NUL byte. `tests/postgres_strict.py` (installed by conftest for every engine) refuses all three the way Postgres does, and `tests/test_input_sweep.py` posts oversized, NUL, out-of-range and malformed values into every field of every student route and fails on any 500 or alert: add a new route or field to it. In the app, every engine strips NUL from bound strings (`_no_nul_in_parameters` in tutor/db/models.py), so no route has to; any id or number from a client goes through `bounded_int` in tutor/routers/params.py ("not given" past 2^31 or when not a number, so a hand-edited parameter falls back to the page's default); and a route that waits on something slow (a stream, ElevenLabs, vision, the grader) commits its request session first, because FastAPI closes it only after the response is sent (`tests/test_pool_release.py`). A hand-edited address opens a page, never JSON: a number in a page's query string is read with `int_query` or `optional_int` (the default when garbled, never `Query(int)`), a number in a path is a `str` parsed with `bounded_int` (a 404 page when it is not one), and the `RequestValidationError` handler in tutor/main.py routes anything left through the 4xx page path (a path segment as 404). A form posted, or a deck frame opened, with a lapsed session goes to the login page (the frame gets `signed_out_frame.html`, whose link signs in the whole page); `test_a_hand_edited_address_is_a_page_never_json` in the sweep checks every page.

- **The daily rollup and the status rule.** `student_days` ([tutor/student_days.py](tutor/student_days.py)) holds one row per student per local day (`tutor.timezone` in courses.yaml) with any activity, folded from the raw tables by the same pure functions the offline analysis uses (`compute`), ids and counts only. The app writes it: `refresh` runs from the admin Today panel and the instructor dashboard, throttled to one pass per 15 minutes per process, recomputing today and yesterday every pass; `python -m tutor.student_days --days N` backfills. The daily-report workflow stays read-only. The Today panel's "Where students stand" card and the export read it; the instructor pages and the Sunday email compute their percentile table live from `class_metrics.standings` (rank only, nothing under five students, staff unranked). A roster row's status comes from `class_metrics._status`: active (asked), reading only (browser events, no question), could not sign in, went quiet, signed in and never asked, never signed in. `is_staff` in [tutor/auth/access.py](tutor/auth/access.py) keeps admins and instructors out of every median and percentile; `engagement.live_thresholds()` reads the heartbeat from config.

- **Spend caps and quotas.** Two class-wide caps live in the Render environment (`DAILY_EXCHANGE_LIMIT` turns per student per local day, `MONTHLY_COST_CAP_USD` for everyone, month to date), and three per-student dollar quotas live in the `settings` table, edited on Admin → Supervision ([tutor/quotas.py](tutor/quotas.py): a local calendar day, week from Monday, and month; defaults $1.50, $6, $15; 0 off). All are checked in `usage.over_caps` inside `run_turn` and in `usage.over_review_caps`, and the quotas again before a photo transcription; admins are exempt from the quotas; the prompt-cache warm-up never counts against a student. A blocked student reads an in-voice message naming when the quota comes back, the chat shows the remaining budget from 80 percent (`GET /chat/quota`), and a hit is one zero-cost `quota` ledger row per student, window and period, which the Today panel, the Supervision tab, and `scripts/quota_report.py` (the daily, weekly, monthly roll-up emails the same tab switches on) read. Every refusal names when it lifts (`usage.daily_limit_message`, `monthly_cap_message`, `review_limit_message`; the class month is the UTC month), the budget line (`usage.cap_indicator`, merged into `/chat/quota`) reports the class caps too, and a capped turn's `done` carries `limited: true`: the page puts the unsaved question back in the box (and keeps it as a draft until the limit lifts), gives the notice no speaker or thumbs, and holds every way of sending until the line clears. When several limits stop a student the notice and the line name the one that lifts last (`usage._limits`, `_latest`). A photo read is ledgered as kind `vision` and checked against the quotas and the class budget (`usage.over_spend_caps`). A message is at most `MAX_MESSAGE_CHARS` (30,000) in the page and on the server, older pastes go back to the tutor clipped (`memory.HISTORY_PASTE_CHARS`), and the graders read an answer's head and end (`mastery.EXAM_ANSWER_CHARS`, `PROBE_ANSWER_CHARS`).

- **Classes and their instructors.** A class (`classes`, [tutor/classes.py](tutor/classes.py), the only writer) is a named roster in one course with one or more instructors: every instructor has a `class_instructors` row, the lead (`classes.instructor_id`) included, and `can_view_class`, `classes_for_instructor` and the weekly email all read that table. Any instructor of a class, or an admin, adds another or removes one from the class's Instructors block (Admin → Classes with a class open; the instructor dashboard's roster view), never themselves and never the last; removing the lead promotes the longest-standing co-instructor. `add_instructor` grants `students.is_instructor` but not login access (the whitelist), and the page's note says when the whitelist would keep the new instructor out.

- **Feedback.** A thumbs on a reply names it by `message_id` (the stream's `done` event and `/chat/history` carry it, and history carries the rating the student already gave); the reply's text is the fallback. `state.record_message_feedback` keeps the latest opinion on `message_feedback` and every rating on `feedback_events`; every message carries its `turn_id`. One link opens a flag for whoever reads it: `GET /feedback/{feedback_id}` ([tutor/routers/feedback.py](tutor/routers/feedback.py)) sends an admin to the admin transcript and a class instructor to their transcript view, each opened around the message (`conversations.thread_around`) and highlighted (`:target`); the daily email and the Today panel link there. A flag has a seen mark (Admin → Today).

- **Recent conversations.** The admin Conversations tab and `/instructor?view=conversations` open on a list of conversations, not an email box. A conversation is one student's run of messages with gaps under 30 minutes, computed at render time by [tutor/conversations.py](tutor/conversations.py) from one query over the window (7 days by default, 200 rows); turns join by time, feedback by message id. The routers only scope and link: the admin sees everyone, cost, and links to Timeline, Supervision and Logins; an instructor sees their roster in the class's course, no cost. The table, the phone cards, the sort links and the filters are one macro (`_conversations_list.html`); the bubbles are one macro (`_conversation_bubbles.html`) that the transcript view, the thread fragments (`/admin/conversations/thread`, `/instructor/conversations/thread`, expanded in place by `conversations.js`) and `/instructor/transcript/view` share. "New since your last visit" is a cookie holding the previous sitting (`conversations.seen_state`), never a table. The transcript view with `?student=` keeps its URL: the thumbs-down email deep-links to it.

- **Single-instance assumption (do not scale to 2+ Render instances without revisiting).** The magic-link rate limiter ([tutor/routers/auth.py](tutor/routers/auth.py)), the `/healthz` per-address limit and probe slots ([tutor/routers/status.py](tutor/routers/status.py)), alert dedup/caps ([tutor/alerts.py](tutor/alerts.py)), self-heal cooldown ([tutor/selfheal.py](tutor/selfheal.py)), the per-student in-flight turn claims (`_INFLIGHT`) in [tutor/agent/turn.py](tutor/agent/turn.py), the review grade's claim per student and goal (`_GRADING` in [tutor/routers/review.py](tutor/routers/review.py)), the reply buffers a reloaded page reattaches to (`streambuf.running_for`, `/chat/running`), the daily photo slots (`vision.allow`), and the activity events' per-student cap ([tutor/activity_events.py](tutor/activity_events.py)) all keep state in process memory. On one instance that is a deliberate, documented trade-off; on two instances the limits double and dedup silently breaks. If horizontal scaling ever becomes necessary, move this state to Postgres first.

## Gitignored, large, or external

- `source-materials/`: an adopter's raw course files (decks, PDFs, recordings, exam keys, anything with student work). Never commit them.
- `knowledge-base/chromadb/`: the vector store (rebuild with `python -m pipeline index --rebuild`). `knowledge-base/raw/` (the extracted text) is tracked.
- `output/`: generated decks and audio, except each lecture's `content.md`, which is tracked.
- `curriculum/mastery_exams.json`: the generated exam bank.
- `.venv/`, `.env`, `tutor.db` (SQLite, regenerated on first run).
